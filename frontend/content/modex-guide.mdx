<Banner>
{{APP_TITLE}} 用来把团队文档从 Git 仓库同步到统一门户，并让 AI 工具通过 MCP 读取这些文档。

## 先确认归属

同步文档前，先确认文档应该放到哪个分类下。

<Steps>
  <Step title="确认分类">
    如果分类已经存在，先联系该分类的负责团队或负责人；如果要新建顶级分类，找平台超级管理员创建。
  </Step>
  <Step title="创建文档源">
    到「管理控制台 / 文档源管理」创建文档源，选择文档类型、归属分类和负责团队。
  </Step>
  <Step title="复制 Deploy Token">
    保存文档源后复制 Deploy Token。这个 token 只用于该文档源的同步，不要提交到仓库。
  </Step>
</Steps>

<Note>
不确定找谁时，先在分类信息里看负责团队；没有负责团队或需要建顶级分类时，联系平台超级管理员。
</Note>

## 同步文档

文档仓库可以通过 GitLab CI 自动同步，也可以由维护人下载 `docsctl` 后手动同步。生产环境推荐 GitLab CI；临时补发、首次排查或没有 CI 权限时，可以用手动方式。

<Tabs>
  <Tab title="GitLab CI 自动同步">

执行流水线的 Runner 需要支持 Docker；如果团队 Runner 用 tag 区分机器，示例里可以使用 `docker`。

把下面内容复制到文档仓库的 `.gitlab-ci.yml`：

```yaml
include:
  - project: "songkwon/modex-fscut"
    ref: "main"
    file: "deploy/ci/modex-docs.gitlab-ci.yml"

modex-docs-deploy:
  tags:
    - docker
```

然后到 GitLab `Settings > CI/CD > Variables` 添加变量：

```text
MODEX_DEPLOY_TOKEN=<从 Modex 文档源复制的 Deploy Token>
```

把 `MODEX_DEPLOY_TOKEN` 设为 Masked；生产分支建议同时设为 Protected。之后 GitLab 默认分支流水线会自动执行 `docsctl deploy`，完成校验、构建、打包和上传。

<Note>
如果你的 GitLab Runner 不使用 `docker` 这个 tag，把示例里的 `tags` 改成团队实际可用、且支持 Docker 的 Runner tag。
</Note>

  </Tab>
  <Tab title="docsctl 手动同步">

在文档仓库根目录执行下面命令。`MODEX_DEPLOY_TOKEN` 使用对应文档源的 Deploy Token；`docsctl` 二进制和部署端点由平台维护方提供：

```bash
chmod +x docsctl

export MODEX_DEPLOY_TOKEN="<从 Modex 文档源复制的 Deploy Token>"
export DOCS_SOURCE_DIR="."
export DOCS_VERSION="latest"

./docsctl deploy
```

如果文档不在仓库根目录，把 `DOCS_SOURCE_DIR` 改成真实文档目录，例如 `docs` 或 `website`。

<Warning>
手动同步适合临时补发和排查问题。长期维护的文档源仍建议接入 GitLab CI，避免 token 留在个人电脑或操作记录里。
</Warning>

  </Tab>
</Tabs>

## 常见文档路径

大多数仓库只需要改 `DOCS_SOURCE_DIR`。

```yaml
variables:
  DOCS_SOURCE_DIR: "docs"
```

常见写法：

| 文档位置 | `DOCS_SOURCE_DIR` |
| --- | --- |
| 文档就在仓库根目录 | `"."` |
| 文档在 `docs/` | `"docs"` |
| 文档在 `website/` | `"website"` |
| 多包仓库里的某个文档 | `"packages/foo/docs"` |

如果一个仓库要同步多个文档源，就建多个 CI job，每个 job 使用自己的 token 和路径：

```yaml
include:
  - project: 'songkwon/modex-fscut'
    ref: main
    file: 'deploy/ci/modex-docs.gitlab-ci.yml'

modex-docs-deploy:
  rules:
    - when: never

tools:
  extends: .modex-docs-base
  rules:
    - changes:
        - "docs/readme/tools/**/*"
  tags:
    - docker
  variables:
    DOCS_SOURCE_DIR: docs/readme/tools
    MODEX_DEPLOY_TOKEN: "$MODEX_DEPLOY_TOKEN_TOOLS"

cloud_services:
  extends: .modex-docs-base
  rules:
    - changes:
        - "docs/readme/service/**/*"
  tags:
    - docker
  variables:
    DOCS_SOURCE_DIR: docs/readme/service
    MODEX_DEPLOY_TOKEN: "$MODEX_DEPLOY_TOKEN_CLOUD_SERVICES"
```

<Warning>
`.modexignore` 也按 `DOCS_SOURCE_DIR` 计算路径。例如 `DOCS_SOURCE_DIR=docs` 时，排除 `docs/drafts` 只需要写 `drafts/`。
</Warning>

## GitLab CI 变量

模板支持这些变量。除了文档源自己的 Deploy Token，其他地址类变量一般由平台模板或 CI 环境统一维护，不建议写在业务仓库的 `.gitlab-ci.yml` 里。

| 变量 | 说明 |
| --- | --- |
| `MODEX_DEPLOY_TOKEN` | 文档源的 Deploy Token。每个文档源使用自己的 token，建议放在 GitLab CI/CD Variables。 |
| `DOCS_SOURCE_DIR` | 文档源目录。默认是仓库根目录 `.`。 |
| `DOCS_VERSION` | 同步到 Modex 的文档版本。默认 `latest`。 |
| `DOCS_PACKAGE_VERSION` | 文档对应的软件包版本。 |
| `DOCS_DESCRIPTION` | 文档源描述。 |
| `DOCS_EDITION` | 文档版本补充标识，例如产品线或发行版。 |
| `DOCS_BUILDER` | 文档框架类型；不填时由 `docsctl` 自动识别。 |
| `DOCS_ENTRY_KEY` | 没有 `docs.yaml` 时生成的入口 key。 |
| `DOCS_ENTRY_TITLE` | 没有 `docs.yaml` 时生成的入口标题。 |
| `DOCS_ENTRY_SOURCE` | 没有 `docs.yaml` 时生成的入口源码目录。 |
| `DOCS_BUILD` | 自定义构建命令，例如静态站需要先执行 npm 构建。 |
| `DOCS_OUTPUT` | 自定义构建产物目录。 |
| `DOCS_BUILD_DIR` | `docsctl build` 的临时构建目录。 |
| `DOCS_ARTIFACT` | `docsctl package` 生成的 zip 包路径。 |
| `DOCS_REWRITE_BASE` | 是否改写构建产物里的根路径资源引用，默认开启。 |
| `DOCS_REPO_URL` | 文档源码仓库地址，GitLab CI 模板默认读取当前项目地址。 |
| `DOCS_REPO_TYPE` | 源码仓库类型，例如 `git` 或 `svn`。 |
| `DOCS_BRANCH` | 文档源码分支，GitLab CI 模板默认读取当前分支。 |
| `DOCS_COMMIT_SHA` | 文档源码提交 SHA，GitLab CI 模板默认读取当前提交。 |
| `MODEX_DOCS_IMAGE` | CI job 使用的 Docker 镜像。 |
| `MODEX_DEPLOY_URL` | Modex 部署端点，由平台维护方提供或统一注入。 |
| `MODEX_DOCSCTL_URL` | `docsctl` 下载地址，由平台维护方提供或统一注入。 |

### 按目录变化触发

如果只希望某个目录有文件变化时才同步，可以用 `rules: changes`：

```yaml
docs:
  extends: .modex-docs-base
  rules:
    - changes:
        - "docs/**/*"
  tags:
    - docker
  variables:
    DOCS_SOURCE_DIR: docs
```

## 文档类型

`docsctl` 会自动识别常见文档项目。识别不准时再手动指定：

```yaml
variables:
  DOCS_SOURCE_DIR: "docs"
  DOCS_BUILDER: "vitepress"
  DOCS_BUILD: "npm ci && npm run docs:build"
  DOCS_OUTPUT: "docs/.vitepress/dist"
```

支持的 `DOCS_BUILDER`：

| 类型 | 适用场景 |
| --- | --- |
| `markdown` | 普通 Markdown 文档 |
| `vitepress` | VitePress 文档站 |
| `vuepress` | VuePress 文档站 |
| `fumadocs` | Fumadocs 文档站 |
| `docusaurus` | Docusaurus 文档站 |
| `mkdocs` | MkDocs 文档站 |
| `honkit` | HonKit 文档站 |
| `gitbook` | GitBook 文档站 |
| `static` | 已经构建好的 HTML 静态目录 |

### 静态资源路径

VitePress、VuePress 等静态站建议在配置里读取 `DOCS_BASE`：

```ts
export default defineConfig({
  base: process.env.DOCS_BASE || "/",
})
```

如果项目设置了非常规输出目录，CI 提示找不到 build output，再补 `DOCS_OUTPUT`：

```yaml
variables:
  DOCS_SOURCE_DIR: "."
  DOCS_BUILDER: "vitepress"
  DOCS_BUILD: "npm ci && npm run docs:build"
  DOCS_OUTPUT: "docs/dist/rd/standards"
```

## Markdown 拆分入口

普通 Markdown 文档源支持两种挂载方式：

| 挂载方式 | 效果 |
| --- | --- |
| `single` | 整个文档源作为一个入口 |
| `split` | 按顶层目录拆成多个入口 |

`split` 只对普通 Markdown 生效。VitePress、VuePress、Fumadocs、Docusaurus、MkDocs 和静态站固定按 `single` 处理。

## 排查问题

### CI 提示 token 无效

检查三件事：

- `MODEX_DEPLOY_TOKEN` 是否来自对应文档源；
- GitLab 变量名是否写成 `MODEX_DEPLOY_TOKEN`；
- Protected 变量是否允许当前分支使用。

### 找不到文档或构建产物

先确认路径：

```bash
pwd
ls
ls "$DOCS_SOURCE_DIR"
```

如果是静态站，再确认构建产物：

```bash
npm ci
npm run docs:build
find . -maxdepth 4 -type d \( -name dist -o -name build \)
```

找到真实产物目录后，把它写到 `DOCS_OUTPUT`。

### 不想同步某些文件

在 `DOCS_SOURCE_DIR` 下创建 `.modexignore`：

```gitignore
drafts/
*.local.md
**/*.draft.md
```

docsctl 默认会跳过 `.git/`、`node_modules/`、`dist/`、`build/`、`.github/`、`.vscode/`，以及 `CLAUDE.md`、`AGENTS.md` 等常见工具说明文件。

<Danger>
不要把 Deploy Token 写进 `.gitlab-ci.yml` 或仓库文件。Token 只放在 GitLab CI/CD Variables 或团队统一的 secret 管理系统里。
</Danger>
